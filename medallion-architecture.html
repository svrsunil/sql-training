What is ETL?

ETL stands for Extract, Transform, Load. It's the process of pulling data out of source systems ("Extract"), cleaning and reshaping it — joining tables, applying calculations, removing bad rows — ("Transform"), and then writing the result somewhere it can be used, like a reporting table ("Load").

In our case study: SAP, the M2M rate system, the inventory system, and the currency system are the sources. The transformation is everything we practiced on the previous page — joins, netting off damage, adjusting for stock, converting currency. The "load" is writing the final result somewhere a report or dashboard can read it.

What is Medallion Architecture?

Medallion Architecture is a simple way of organizing that ETL process into three layers, each one cleaner than the last:

  • Bronze — raw data, landed as-is, no changes
  • Silver — cleaned, joined, and adjusted data
  • Gold — aggregated, business-ready data used for reporting

Data flows one direction: Bronze → Silver → Gold. Each layer is a table (or set of tables) in its own right, not just a temporary step — so you can always go back and check what the raw data looked like before any transformation happened.

Bronze

Raw data, as received from each source. No joins, no calculations.

→

Silver

Cleaned and joined. Damage netted off, prices adjusted, currency converted.

→

Gold

Aggregated and tagged for accounting. Ready for dashboards and reports.

Bronze Layer — Raw Sources

Four raw tables, landed exactly as they come from their source systems — no transformation at all:

TableSource systemWhat it contains
contractsSAPFinished good/raw material mapping, contract dates, shippers, SOP quantities, USD rate
m2m_ratesM2M systemRejection/paddy byproduct rate list
inventory_damageInventory systemDamaged item records per contract
currency_ratesCurrency systemDaily USD → INR conversion rates

At Bronze, nothing is joined and nothing is calculated. If SAP sends a typo, Bronze has the typo too — that's expected, it's a raw copy.

Silver Layer — Cleaned & Joined

This is where the joins from the practice page happen. Silver takes the Bronze tables and:

  • LEFT JOINs contracts to inventory_damage so every contract is kept, even ones with no damage
  • GROUP BYs the damage records per contract, then nets them off total_sop to get pending_sop
  • INNER JOINs to stock_levels to apply the stock-based price adjustment
  • INNER JOINs to currency_rates (matched by date) to convert the rate to INR

The result is one clean row per contract, with pricing and currency already sorted out — but not yet aggregated for reporting.

See Part 1 and Part 3 of the SQL Practice page for the exact join logic used here.

Gold Layer — Reporting-Ready

Gold takes the Silver output and tags/aggregates it for business use — this is where the GROUP BY and window function logic from the practice page comes in:

  • Joins to gl_accounts to tag each row with a GL code, so finance can slice the report by ledger account
  • GROUP BY shipper or GROUP BY gl_code for management summaries
  • RANK() to show top shippers by sales value
  • Running totals (SUM() OVER (...)) to track cumulative sales over time per shipper

This is the Final Output table — the one a BI dashboard or finance report would actually query. It's small, aggregated, and business-friendly compared to the raw Bronze tables.

LayerRow count (this example)Used by
Bronze4 raw tables, ~20 rows totalData engineers, auditing/debugging
Silver6 rows (one per contract, enriched)Analysts building reports
Gold6 rows, tagged with GL codes, or fewer if grouped by shipperDashboards, finance, management reporting

Why bother with three layers instead of one big query?

  • Debugging: if a number looks wrong in the report, you can check Silver, then Bronze, to find exactly where it went wrong
  • Reuse: Silver can feed more than one Gold report without redoing the joins each time
  • Trust: Bronze is never modified, so you always have an unaltered copy of what the source system actually sent
